# Аким на 5 часов: AI-симулятор управления городом

Команда AVM AI, хакатон HackAlem AI, 23.09.2026. Задача 12, спец-трек Astana Innovations. Условия задачи: [docs/tracks/12-akim-tz.md](docs/tracks/12-akim-tz.md).

## Описание и назначение

Пользователь в роли акима получает бюджет 100 условных единиц и выбирает ровно пять городских мер из каталога 14 по пяти направлениям: транспорт, экология, соцсфера, безопасность, сервисы. Симулятор считает Astana Quality of Life Score по формуле из ТЗ, показывает, как изменились пять районов, находит проверяемое улучшение заменой одной меры и даёт AI-объяснение результата: сильные стороны, риски, компромиссы.

Модель учебная: районы, показатели и эффекты мер заданы условиями задачи и не являются данными о реальном бюджете Астаны.

Назначение: инструмент для обучения и обсуждения городского бюджета, где видно не только итоговую цифру, но и почему она такая, что стало со слабейшим районом и чем пришлось пожертвовать.

## Архитектура

```
Браузер (static/)  ──HTTP JSON──▶  FastAPI (app.py)
                                      │
                                      ├─ engine/model.py       загрузка и проверка data/city.json
                                      ├─ engine/validator.py   правила набора
                                      ├─ engine/scoring.py     формула Score, разложение прироста
                                      ├─ engine/advisor.py     поиск улучшения заменой одной меры
                                      ├─ engine/facts.py       факты для объяснения, резервный текст
                                      └─ engine/explain.py     OpenAI: объяснение по фактам, проверка ответа
                                            │
                                      data/city.json          районы, меры, правила из ТЗ
```

Расчёт детерминирован и выполняется на сервере по данным из `data/city.json`. Браузер отправляет только идентификаторы мер и районов. LLM получает уже посчитанные числа и объясняет их, сам ничего не считает. Без ключа модели приложение работает полностью, объяснение собирается из тех же фактов шаблоном и помечается как резервный режим.

Подробная спецификация: [docs/akim-spec.md](docs/akim-spec.md). План реализации бэкенда: [docs/akim-backend-plan.md](docs/akim-backend-plan.md).

## Проверка основного сценария

### Через API

Сервер запущен на порту 8000. Пример из ТЗ: M7 Нура, M8 Нура, M10 Нура, M12 город, M5 Сарыарка.

1. Данные одинаковы для всех, база без действий:
   ```
   curl -s localhost:8000/api/city
   ```
   В ответе `"budget": 100`, 5 районов, 14 мер, `baseline.score = 52.55768`, два критических показателя в Нуре (S1 = 38, S2 = 35).

2. Расчёт Score для примера из ТЗ:
   ```
   curl -s -X POST localhost:8000/api/evaluate -H "Content-Type: application/json" -d '{"decisions":[{"measure_id":"M7","district_id":"nura"},{"measure_id":"M8","district_id":"nura"},{"measure_id":"M10","district_id":"nura"},{"measure_id":"M12"},{"measure_id":"M5","district_id":"saryarka"}]}'
   ```
   Ожидание: `"valid": true`, `"cost": 95`, `"score": 56.54307`, `"delta": 3.98539`, `"critical_count": 0`, синергия `M10+M12`, разложение прироста `avg 0.85064`, `min 1.13475`, `crit 2.0`. В `district_results` у каждого показателя значения `before` и `after`.

3. Контроль бюджета. Набор M3 Есиль, M13 Алматы, M5 Сарыарка, M7 Нура, M12 стоит 121:
   ```
   curl -s -X POST localhost:8000/api/evaluate -H "Content-Type: application/json" -d '{"decisions":[{"measure_id":"M3","district_id":"esil"},{"measure_id":"M13","district_id":"almaty"},{"measure_id":"M5","district_id":"saryarka"},{"measure_id":"M7","district_id":"nura"},{"measure_id":"M12"}]}'
   ```
   Ожидание: `"valid": false`, `"score": null`, ошибка `budget_exceeded` с текстом «Превышен бюджет на 21: стоимость 121 при лимите 100». Так же отклоняются 4 или 6 решений, повтор меры, третья мера одного направления, несовместимые M1 и M3.

4. Изменение набора меняет Score. Заменить в примере M5 Сарыарка на M14 (город):
   ```
   curl -s -X POST localhost:8000/api/evaluate -H "Content-Type: application/json" -d '{"decisions":[{"measure_id":"M7","district_id":"nura"},{"measure_id":"M8","district_id":"nura"},{"measure_id":"M10","district_id":"nura"},{"measure_id":"M12"},{"measure_id":"M14"}]}'
   ```
   Ожидание: `"cost": 86`, `"score": 56.98582`, другой `scenario_key`.

5. Улучшение заменой одной меры:
   ```
   curl -s -X POST localhost:8000/api/improvements -H "Content-Type: application/json" -d '{"decisions":[{"measure_id":"M7","district_id":"nura"},{"measure_id":"M8","district_id":"nura"},{"measure_id":"M10","district_id":"nura"},{"measure_id":"M12"},{"measure_id":"M5","district_id":"saryarka"}]}'
   ```
   Ожидание: три кандидата, лучший `c1` заменяет M5 Сарыарка на M3 Нура: Score 57.20556, прирост +0.66249 к набору пользователя, стоимость 100.

6. AI-объяснение:
   ```
   curl -s -X POST localhost:8000/api/explain -H "Content-Type: application/json" -d '{"decisions":[{"measure_id":"M7","district_id":"nura"},{"measure_id":"M8","district_id":"nura"},{"measure_id":"M10","district_id":"nura"},{"measure_id":"M12"},{"measure_id":"M5","district_id":"saryarka"}]}'
   ```
   Без ключа: `"mode": "fallback"`, `"reason": "not_configured"`, объяснение собрано из 19 фактов: резюме, сильные стороны, риски, три предложения. С ключом в `.env`: `"mode": "live"`, `"model": "gpt-4o-mini"`, каждое утверждение ссылается на `fact_ids`.

Трактовка правил: используются подробные правила приложения к ТЗ. Ровно 5 решений, не более 2 мер из одного направления, из чего следует минимум 3 направления. Пример из ТЗ этому соответствует.

### Формула и контрольный пример

Для каждого района и показателя: `I' = clip(I + Σ эффект × (8 − лаг)/8 + синергии, 0, 100)`. Оценка района `D = Σ w_k × I'_k`, средневзвешенное по населению `D_avg`, `Score = 0.7 × D_avg + 0.3 × min(D) − N_crit`, где `N_crit` это число пар «район × показатель» строго ниже 40. Обрезка 0–100 выполняется один раз после суммирования, округляется только вывод.

База без действий: `D_avg 56.8624`, `min 49.18`, `N_crit 2`, Score `52.55768`. Пример из ТЗ: стоимость 95, `D_avg 58.0776`, `min 52.9625`, `N_crit 0`, Score `56.54307`, прирост `3.98539 = 0.85064 (среднее) + 1.13475 (слабейший район) + 2.0 (снятый штраф)`. Эти числа закреплены тестами с допуском 1e-6.

### Режимы объяснения: live и fallback

- `live`: сервер передаёт модели только посчитанные факты `f1…fN` и идентификаторы альтернатив `c1…c3`. Ответ проверяется: строгая JSON-схема, все `fact_ids` и `candidate_id` существуют, любое число в тексте совпадает с числом из фактов. Нарушение, таймаут или сетевая ошибка переводят ответ в `fallback`.
- `fallback`: объяснение собирается из тех же фактов по правилам без модели, ответ помечен `mode: fallback` и причиной (`not_configured`, `JSONDecodeError`, `TimeoutError` и т.д.). Интерфейс показывает пометку «AI-советник недоступен, показано вычисленное объяснение».
- Проверка чисел программная; качественные утверждения модели могут требовать оценки человеком. Живой режим покрыт тестами с подменённой моделью; реальный запрос к OpenAI командой не проверялся, так как на момент сдачи у команды не было ключа. Без ключа весь сценарий проходит в `fallback`.

### Ограничение советника

`/api/improvements` перебирает замену одной меры на любую меру каталога с любым допустимым районом (до 270 вариантов), каждый кандидат проходит валидатор и расчёт. Возвращаются до трёх строгих улучшений, это «лучшее среди замен одной меры», а не глобальный оптимум. Если улучшений нет, список пуст.
