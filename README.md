# Аким на 5 часов: AI-симулятор управления городом

Команда AVM AI, хакатон HackAlem AI, 23.09.2026. Задача 12, спец-трек Astana Innovations. Условия задачи: [docs/tracks/12-akim-tz.md](docs/tracks/12-akim-tz.md).

## Описание и назначение

Пользователь в роли акима получает бюджет 100 условных единиц и выбирает ровно пять городских мер из каталога 14 по пяти направлениям: транспорт, экология, соцсфера, безопасность, сервисы. Симулятор считает Astana Quality of Life Score по формуле из ТЗ, показывает, как изменились пять районов, находит проверяемое улучшение заменой одной меры и даёт AI-объяснение результата: сильные стороны, риски, компромиссы.

Модель учебная: районы, показатели и эффекты мер заданы условиями задачи и не являются данными о реальном бюджете Астаны.

Назначение: инструмент для обучения и обсуждения городского бюджета, где видно не только итоговую цифру, но и почему она такая, что стало со слабейшим районом и чем пришлось пожертвовать.

## Архитектура

```
Браузер (static/)  ──HTTP JSON──▶  FastAPI (app.py)
                                      │
                                      ├─ engine/model.py       загрузка и проверка data/city.json
                                      ├─ engine/validator.py   правила набора
                                      ├─ engine/scoring.py     формула Score, разложение прироста
                                      ├─ engine/advisor.py     поиск улучшения заменой одной меры
                                      ├─ engine/facts.py       факты для объяснения
                                      ├─ engine/templates.py   банк ответов без модели: из фактов и полного перебора
                                      ├─ engine/ranking.py     полный перебор 694 395 допустимых планов, ранг сценария
                                      └─ engine/explain.py     OpenAI: объяснение по фактам, диалог, проверка ответа
                                            │
                                      data/city.json          районы, меры, правила из ТЗ
                                      data/top_sets.json      индекс перебора: топ-100 планов и квантили Score
```

Расчёт детерминирован и выполняется на сервере по данным из `data/city.json`. Браузер отправляет только идентификаторы мер и районов. LLM получает уже посчитанные числа и объясняет их, сам ничего не считает. Без ключа модели приложение работает полностью: объяснение собирается банком ответов из тех же фактов и полного перебора планов и помечается как режим `template`.

### Формула и контрольный пример

Для каждого района и показателя: `I' = clip(I + Σ эффект × (8 − лаг)/8 + синергии, 0, 100)`. Оценка района `D = Σ w_k × I'_k`, средневзвешенное по населению `D_avg`, `Score = 0.7 × D_avg + 0.3 × min(D) − N_crit`, где `N_crit` это число пар «район × показатель» строго ниже 40. Обрезка 0–100 выполняется один раз после суммирования, округляется только вывод.

База без действий: `D_avg 56.8624`, `min 49.18`, `N_crit 2`, Score `52.55768`. Пример из ТЗ: стоимость 95, `D_avg 58.0776`, `min 52.9625`, `N_crit 0`, Score `56.54307`, прирост `3.98539 = 0.85064 (среднее) + 1.13475 (слабейший район) + 2.0 (снятый штраф)`. Эти числа закреплены тестами с допуском 1e-6.

### Режимы объяснения: live и template

- `live`: сервер передаёт модели только посчитанные факты `f1…fN` и идентификаторы альтернатив `c1…c3`. Ответ проверяется: строгая JSON-схема, непустые сильные стороны и риски, все `fact_ids` и `candidate_id` существуют, каждое число в утверждении встречается среди чисел именно тех фактов, на которые утверждение ссылается (с допуском на округление), плюс короткий список констант задачи: 1–5, 8, 40, 100. Резюме сверяется с фактами об оценке, районах и критических значениях. Это лексическая проверка: она отсекает числа, которых нет в расчёте, но не подтверждает смысл фразы. Нарушение, таймаут или сетевая ошибка переводят ответ в `template`.
- `template`: банк ответов без модели. Тексты собираются из тех же фактов, правил и полного перебора планов (`engine/templates.py`): резюме с рангом среди всех допустимых планов, сильные стороны, риски (в том числе упущенные синергии и непотраченный бюджет), предложения, сравнение с лучшим планом. Ответ помечен `mode: template` и причиной (`not_configured`, `JSONDecodeError`, `TimeoutError` и т.д.). Интерфейс показывает на панели советника метку «банк ответов», а при живом ответе «AI · ключ сервера» или «AI · ваш ключ».
- Диалог `POST /api/chat` доступен только с ключом (серверным или из заголовка). Поле `numbers_checked` — лексическая проверка: каждое число ответа встречается среди чисел расчёта и топа планов. Смысл утверждений она не подтверждает; при `false` интерфейс показывает пометку «числа не сверены с расчётом».
- Проверка чисел программная; качественные утверждения модели могут требовать оценки человеком. Живой режим и диалог покрыты тестами с подменённой моделью и проверены командой на реальном ключе OpenAI 23.09.2026 (модель `gpt-4o-mini`): объяснение примера из ТЗ прошло проверку схемы и чисел, диалог ответил с `numbers_checked: true`. Без ключа весь сценарий проходит в `template`.

### Ограничение советника

`/api/improvements` перебирает замену одной меры на любую меру каталога с любым допустимым районом (до 270 вариантов), каждый кандидат проходит валидатор и расчёт. Возвращаются до трёх строгих улучшений, это «лучшее среди замен одной меры». Если улучшений нет, список пуст.

Глобальную картину даёт индекс `data/top_sets.json`: он построен полным перебором всех 694 395 допустимых планов (`python scripts/rank_all.py`, около 20 секунд на CPU) и хранит топ-100 планов и 1000 квантилей Score. `GET /api/top` отдаёт лучшие планы, поле `rank` в `/api/evaluate` — процентиль плана (доля планов не лучше данного), позицию в топ-100 и разрыв до лучшего. Поле `pareto` в `/api/top` — Парето-граница «стоимость → лучший Score»: для каждого уровня бюджета лучший план, оставлены только строгие улучшения; она показывает, сколько стоит каждый следующий балл. Лучший план по этой модели: 57,23673 за 98 единиц; сам по себе он не является рекомендацией для реального города.

## Патруль Go2: путь к реальным данным о безопасности

Показатели безопасности B1, B2, а также E2 и C1 в учебной модели условны. В реальном внедрении их могут питать данные с камер Safe City (проект Astana Innovations) и с патрульного робота-собаки Unitree Go2 — действующего прототипа команды (Astana Dynamics, репозиторий `go2-mvd-system`): робот отдаёт видеопоток H.264 640×480@15 fps по RTSP в центр оперативного управления, детектирует объекты (YOLO11n, 80 классов, трекинг) и проходит маршрут по точкам с порогом прибытия 1,5 м. Во вкладке «Безопасность» интерфейса показан концепт такого патруля: маркер робота на схеме районов, панель камеры и лента комментариев ИИ-агента о дефектах городской среды и ситуациях (открытые люки, ямы, скопления людей, показания газоанализатора), каждое событие привязано к району и показателю. Данные в этом блоке демонстрационные, к живому роботу ничего не подключено, официальный Score они не меняют; классы городских дефектов, газоанализатор и привязка событий к районам — следующий шаг после хакатона.
