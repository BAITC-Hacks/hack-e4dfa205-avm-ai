# Хакатон: правила работы

Мы решаем задачу на хакатоне. Ниже правила, которым обязаны следовать все агенты (архитектор, исполнитель) при работе над решением. Нарушение ведёт к дисквалификации команды или недопуску к проверке.

## Выбранная задача

**Задача 12. Спец-трек Astana Innovations: «Аким на 5 часов», AI-симулятор управления городом.** Полный текст ТЗ и дополнительный документ с данными: ссылки в начале README. Ниже условия в сжатом виде; при расхождении верен полный текст.

**Суть.** Пользователь в роли акима получает фиксированный виртуальный бюджет и данные о состоянии условных районов города, принимает 5 управленческих решений по пяти направлениям (транспорт, озеленение, социальная инфраструктура, безопасность, городской сервис) и получает итоговый Astana Quality of Life Score с объяснением влияния решений. AI анализирует выбранные решения, их стоимость и влияние на показатели, формирует оценку сценария и рекомендации.

**Must have.**
- Единый виртуальный бюджет для всех пользователей.
- Возможность принять решения по 5 заданным направлениям.
- Автоматический контроль превышения бюджета.
- AI-анализ принятых решений.
- Расчёт итогового Astana Quality of Life Score.
- Объяснение сильных сторон, рисков и возможных последствий выбранного сценария.

**Опционально.** Сравнение результатов нескольких команд; визуализация изменений показателей районов; AI-рекомендации по улучшению сценария; моделирование неожиданных городских событий с перераспределением бюджета; автогенерация краткой презентации решения.

**Критерии проверки.**
1. Все команды начинают с одинакового бюджета и исходных данных.
2. Система не позволяет превысить бюджет.
3. Принятые решения влияют на итоговые показатели модели.
4. AI формирует понятное объяснение результата и основных компромиссов.
5. Изменение набора решений меняет Score.

**Данные, заданы в ТЗ целиком.** 5 районов (Есиль, Алматы, Сарыарка, Байконур, Нура) с долей населения и 10 показателями 0–100 (T1, T2, E1, E2, S1, S2, B1, B2, C1, C2, больше значит лучше). Каталог из 14 мероприятий M1–M14 с направлением, типом (район или город), стоимостью, лагом в кварталах и эффектами. Три синергии (M1+M2, M10+M12, M5+M6) и три несовместимости (M1 и M3; M4 и M7 в одном районе; M5 и M13 в одном районе). Горизонт 8 кварталов, реализованная доля эффекта (8 − L)/8.

**Формула Score.** I'_dk = clip(I_dk + Σ эффект × (8 − L)/8 + синергии, 0, 100); D_d = Σ w_k × I'_dk по весам показателей; D_avg = Σ pop_d × D_d; Score = 0.7 × D_avg + 0.3 × min(D_d) − 1.0 × N_crit, где N_crit это число пар «район × показатель» ниже 40. Базовый Score без действий 52.56. Контрольный набор M7 Нура, M8 Нура, M10 Нура, M12 город, M5 Сарыарка стоит 95 и даёт около 56.5.

**Правила набора.** Бюджет 100 единиц, остаток не сгорает. Решений ровно 5, без повторов. Для районных мер район указывается обязательно, для городских не указывается. Не более 2 мер из одного направления. Несовместимости запрещены. Невалидный набор не получает Score, валидатор возвращает причину. Порядок решений значения не имеет.

**Роль ИИ по ТЗ.** LLM получает результат расчёта (дельты по районам и показателям, вклад каждой меры), объясняет его, сравнивает наборы, советует. Числа он не считает и не придумывает.

**Критерии оценки на техотборе.** Соответствие задаче и работоспособность 25, техническая реализация 25, README и воспроизводимость 25, ценность и применимость 15, потенциал развития и оригинальность 10.

## Репозиторий

- Коммит и push только с разрешения пользователя.
- Вся разработка только в этом репозитории. Другие remote не добавлять, код никуда не переносить.
- История коммитов должна быть подтверждаемой. Запрещены `push --force`, `rebase` и `--amend` для запушенных коммитов, squash истории.
- Коммитить и пушить часто, небольшими шагами, с сообщениями о том, что реально сделано. Организатор проверяет историю, метаданные файлов и вклад участников.
- Нет готового кода к контрольной точке: коммитить схему, README, заготовку, тесты. Пустой промежуток недопустим.

## Проект должен запускаться сам

Технические эксперты Организатора разворачивают, запускают и проверяют проект самостоятельно, только по материалам репозитория, без участия команды. Отсюда требования к коду:

- Запуск одной понятной командой с чистой машины (например `docker compose up` или `make run`). Никаких ручных шагов, которые не описаны в README.
- Все зависимости зафиксированы в файлах проекта (lock-файлы, Dockerfile, requirements). Ничего не ставится «руками».
- Все переменные окружения перечислены в `.env.example` с комментариями. Личные ключи и пароли в репозиторий не попадают.
- Ключевая функциональность проверяется без личных аккаунтов, подписок и закрытых учёток участников. Для внешних API и сервисов: демо-доступ, тестовые учётные записи или демо-режим с заглушкой, в котором основной сценарий проходит без ключей.
- Перед финальным push: запуск с чистой машины строго по README.

## README: условие допуска

Если эксперты не запустят проект по README, команда выбывает без права на пояснения и исправления. README ведётся по ходу работы, а не пишется в конце, и содержит:

- описание решения и его назначения;
- архитектуру;
- технологии;
- системные требования;
- установку;
- запуск;
- зависимости;
- переменные окружения со ссылкой на `.env.example`;
- пошаговую проверку основного сценария работы.

## Сторонние материалы

- Все open-source библиотеки, модели, датасеты, шаблоны, boilerplate раскрываются отдельным разделом README с соблюдением лицензий.
- Чужое решение без указания источника или выдача чужого за своё: дисквалификация.
- Заготовки и инфраструктура допустимы, если сами по себе ещё не готовый продукт. Основная функциональность по задаче создаётся в ходе соревнования.
- AI-инструменты и агенты разрешены без ограничений. Строка Co-Authored-By в коммитах остаётся.
