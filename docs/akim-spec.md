# Спецификация: «Аким на 5 часов», AI-симулятор управления городом

Дата: 23.09.2026, 14:50. Статус: согласована командой и консилиумом (Клод, Астра), принята к реализации. Дедлайн оцениваемой версии 18:00. Источник условий: `docs/tracks/12-akim-tz.md`.

## 1. Что делаем

Веб-приложение, в котором пользователь в роли акима выбирает ровно пять городских мер из каталога 14 в рамках бюджета 100, а система считает Astana Quality of Life Score по формуле из ТЗ, показывает изменения по пяти районам, ищет проверяемое улучшение и даёт AI-объяснение результата.

Успех: шесть must-have и пять критериев проверки ТЗ проходят на любом допустимом наборе, проект запускается по README одной командой на чистой машине с Python, без ключа приложение считает и честно показывает резервный режим объяснения, с ключом объяснение делает OpenAI.

За пределами версии: реальные данные Астаны, геосервисы, регистрация, база данных, многопользовательский рейтинг, голос, события-шоки, PDF. Exa и ElevenLabs в сценарий не входят.

## 2. Стек и запуск

- Python 3.11+, FastAPI, uvicorn, pydantic, openai, pytest. Зависимости зафиксированы в `requirements.txt` с версиями.
- Фронтенд: одна страница `static/index.html` с `app.css` и `app.js`, без сборки и без CDN. Графики рисуются CSS и SVG.
- Запуск на чистой машине:
  ```
  pip install -r requirements.txt
  python -m uvicorn app:app --port 8000
  ```
  Страница на http://localhost:8000. Docker не является основным путём: на машине команды его нет, непроверенная команда в README недопустима.
- Переменные в `.env.example`: `OPENAI_API_KEY` (пусто; без него резервный режим), `OPENAI_MODEL` (по умолчанию `gpt-4o-mini`), `LLM_TIMEOUT_S` (15). Ключ читается только сервером, в браузер не попадает.

## 3. Данные, `data/city.json`

Единственный источник данных, версия `hackalem-12-v1`. Содержит ровно то, что в ТЗ:

- Пять районов с id `esil, almaty, saryarka, baikonur, nura`, названием, долей населения и десятью показателями в порядке T1, T2, E1, E2, S1, S2, B1, B2, C1, C2.
- Веса показателей 0.10, 0.10, 0.09, 0.11, 0.11, 0.11, 0.09, 0.09, 0.10, 0.10.
- Каталог мер M1–M14: направление (`transport, ecology, social, safety, services`), название, тип `district` или `city`, стоимость, лаг, эффекты как словарь показатель → дельта.
- Синергии: M1+M2 → T1 +2 в районе M1; M10+M12 → B1 +2 в районе M10; M5+M6 → E2 +2 в районе M5. Бонус фиксированный, без лага.
- Несовместимости: M1 и M3 в любом районе; M4 и M7 в одном районе; M5 и M13 в одном районе.
- Бюджет 100, горизонт 8 кварталов, порог критического значения 40, коэффициенты 0.7 и 0.3, штраф 1.0.

Данные не редактируются пользователем и не мутируются при расчёте.

## 4. Правила набора, трактовка

Берём подробные правила приложения ТЗ, а не заголовок «5 решений по 5 направлениям»: ровно 5 решений, не более 2 мер из одного направления, из чего следует минимум 3 направления. Пример из ТЗ (2/1/1/1) этому соответствует. Трактовка записывается в README.

| Правило | Поведение валидатора |
|---|---|
| Ровно 5 решений | Иначе невалидно |
| Бюджет ≤ 100 | Остаток не сгорает и не даёт бонуса |
| Каждая мера один раз | Повтор M-id в любом районе невалиден |
| Районная мера | Обязателен существующий район |
| Городская мера | Район не передаётся |
| Не более 2 из направления | Третья невалидна |
| M1 и M3 | Несовместимы независимо от районов |
| M4 и M7, M5 и M13 | Несовместимы только в одном районе |
| Порядок решений | Не влияет на расчёт и ключ сценария |

Невалидный набор: список причин с кодами, `score = null`, LLM не вызывается. Браузер предупреждает сразу, сервер перепроверяет всё и принимает только ID мер и районов.

## 5. Расчёт, `engine/`

1. Скопировать исходные показатели.
2. Для каждой меры прибавить эффект × (8 − лаг) / 8 в район меры или во все районы.
3. Добавить синергии.
4. Обрезать каждый показатель в 0–100 только после суммирования.
5. D_d = Σ w_k × I'_dk по каждому району.
6. D_avg = Σ pop_d × D_d; D_min = min(D_d).
7. N_crit = число пар «район × показатель» строго меньше 40.
8. Score = 0.7 × D_avg + 0.3 × D_min − N_crit. Округление только при выводе.

Разложение прироста: ΔScore = 0.7 × ΔD_avg + 0.3 × ΔD_min − ΔN_crit. Эти три числа показываются пользователю. Вклад меры показывается через её эффекты на показатели, суммирование приростов Score отдельных мер не обещается.

Контрольные значения для тестов: базовые D районов 62.99, 57.06, 54.65, 56.63, 49.18; база D_avg 56.8624, D_min 49.18, N_crit 2, Score 52.55768. Пример ТЗ (M7 Нура, M8 Нура, M10 Нура, M12 город, M5 Сарыарка): стоимость 95, D_avg 58.0776, D_min 52.9625, N_crit 0, Score 56.54307, прирост 3.98539. Самый дешёвый набор M9, M11, M10, M12, M4 стоит 61 и валиден.

Модули: `engine/model.py` (загрузка city.json в dataclass), `engine/validator.py`, `engine/scoring.py`, `engine/advisor.py`, `engine/explain.py`, `engine/facts.py` (факты и резервный текст).

## 6. Советник, `engine/advisor.py`

Для допустимого набора перебрать замену каждой из пяти мер любой мерой каталога с любым допустимым районом, включая перенос той же меры в другой район. До 350 кандидатов, каждый через общий валидатор и расчёт. Дубликаты удаляются по каноническому ключу. В выдачу попадают только улучшения больше 1e-8, сортировка по Score, затем по стоимости. Возвращаются до трёх вариантов: что заменить, на что, район, стоимость, прирост, разложение. Подпись в интерфейсе: «лучшее среди замен одной меры». Если улучшений нет: «Улучшений заменой одной меры не найдено».

## 7. AI-объяснение, `engine/explain.py`

Вход: пакет фактов из расчёта с идентификаторами `f1…fN`: выбранные меры, показатели до/после по районам, три слагаемых прироста, критические пары до/после, активные синергии, вычисленные альтернативы `c1…c3`. Модель получает промпт: объяснить акиму сильные стороны, риски и компромиссы, ссылаясь на факты, числа не придумывать, новые меры не предлагать.

Формат ответа JSON: `summary`, `strengths[]`, `risks[]` с полями `text` и `fact_ids`, `suggestions[]` с `candidate_id`, `text`, `fact_ids`. Сервер проверяет JSON, известность всех `fact_ids` и `candidate_id`, длину. Любая ошибка проверки, таймаут 15 с или отсутствие ключа: режим `fallback`, текст собирается из тех же фактов шаблоном, интерфейс показывает «AI-советник недоступен, показано вычисленное объяснение». Режим `live` возвращает имя модели. Кэш в памяти по ключу сценария и версии данных, не более 100 записей. Ответ несёт `scenario_key`, клиент принимает его только для текущего набора.

## 8. API, `app.py`

| Маршрут | Вход | Выход |
|---|---|---|
| GET /api/health | нет | `status`, `dataset_version`, `ai_configured` |
| GET /api/city | нет | районы, меры, правила, версия |
| POST /api/evaluate | `{decisions: [{measure_id, district_id?}]}` | результат сценария |
| POST /api/improvements | тот же вход | до трёх альтернатив, 422 для невалидного |
| POST /api/explain | тот же вход | `scenario_key, mode, model?, explanation, facts`, 422 для невалидного |

Результат `/api/evaluate`: `valid, errors[], scenario_key, cost, remaining_budget, score, baseline_score, delta, decomposition{avg, min, crit}, average, minimum, critical_count, critical_pairs[], active_synergies[], district_results[]`. Для района: `id, name, population, score_before, score_after, indicators[{code, before, after, critical}]`. Для невалидного набора итоговые поля `null`, HTTP 200 с `valid=false`. Лишние свойства и неизвестные ID отвергаются, тело до 16 КБ.

## 9. Интерфейс, `static/`

Один экран, три колонки на широком экране, последовательные блоки на узком.

- Шапка: название, «учебная модель», бюджет «76 / 100», счётчик «4 / 5», кнопки «Пример из ТЗ», «Сброс», «Как считается».
- Слева: каталог мер по пяти вкладкам направлений. Карточка: название, стоимость, район или город, лаг, эффекты. Выбор района для районной меры. Нарушение правила объясняется словами и не применяется.
- Центр: условная схема пяти районов (SVG, подпись «условная схема, не карта»), цвет по D_d, при раскрытии десять показателей до → после и критические значения. Общий Score крупно с дельтой к базе 52.56, три слагаемых прироста.
- Справа: «Мой план», список пяти мер с районами и стоимостью, кнопки «Найти улучшение», «Объяснить», «Сохранить A / B», сравнение A и B.
- Внизу справа: панель советника: резюме, сильные стороны, риски, альтернативы с кнопкой «Применить» (набор берётся из расчёта, не из текста).

Состояния: неполный набор (база и подсказка, Score не показан), невалидный набор (причины), допустимый (результат), ожидание AI, ошибка AI (резервный текст с пометкой), набор изменился (старый разбор скрыт). Стиль: светлый фон, тёмно-синие заголовки, зелёный для улучшений, янтарный для рисков, цвет всегда с числом или подписью. Сохранение черновика и A/B в localStorage с версией данных.

## 12. Разделение работы и порядок

Процесс по спецификациям: каждый агент пишет свою, команда берёт лучшее из обеих, потом реализация. Файлы не пересекаются. ## 13. Демо на 3–5 минут

1. Проблема: бюджет ограничен, высокий средний балл не должен прятать провал одного района.
2. База 52.56, два критических показателя в Нуре.
3. «Пример из ТЗ»: 95 единиц, Score 56.54, критических нет, три слагаемых прироста.
4. Заменить меру по предложению жюри, показать пересчёт и запрет недопустимой комбинации.
5. «Объяснить»: живой ответ модели со ссылками на факты.
6. «Найти улучшение»: одна проверенная альтернатива, «Применить», компромисс между средним и слабейшим районом.

Готово к сдаче, когда: таблица требований в README заполнена работающими функциями; тесты проходят; чистый запуск по README прошёл; живой AI проверен и способ доступа экспертам описан; ключей в репозитории нет; зависимости и сторонние материалы раскрыты.
