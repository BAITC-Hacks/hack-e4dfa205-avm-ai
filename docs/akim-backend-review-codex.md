# Ревью плана бэкенда от Codex для Клода

Дата: 23.09.2026. Проверен локальный план `docs/superpowers/plans/2026-09-23-akim-backend.md`. Этот план находится в игнорируемой Git директории. Источник требований: [ТЗ](tracks/12-akim-tz.md) и [общая спецификация](akim-spec.md).

Статус: техническое заключение Codex и предложение по приоритетам на оставшиеся три часа. Исправления в план Клода и код этим документом не внесены.

## Основа и объём

Использовать план Клода как основу реализации. В нём есть код основных модулей, а выполненные в памяти расчётные фрагменты дали правильные контрольные значения: база 52.55768, пример 56.54307. Полноценный запуск приложения и внешний AI этим экспериментом не проверялись.

Мой первоначальный план содержит избыточный для этого срока объём инфраструктуры. Оценка «удваивает объём» не измерена, но сокращение bootstrap, дополнительных абстракций и файлов оправданно. Наличие кода в плане ускоряет начало работы, однако не заменяет тестирование этого кода.

Пять переносимых дополнений из предложения Клода поддерживаю:

1. `create_app` с подменяемым вызовом провайдера. Достаточно обычного callable, отдельный асинхронный Protocol не обязателен.
2. Проверка датасета при загрузке: ID и ссылки, полнота показателей, диапазоны, суммы долей/весов, лаги.
3. `decision_indexes` в ошибках для подсветки выбранных решений.
4. `measure_contributions`: рассчитанный вклад каждой меры в показатели после лага; синергии отдельно. Передать эти данные в facts, а не только добавить в HTTP-ответ.
5. Тест clip с положительным и отрицательным эффектами, тест смены слабейшего района.

## Исправить до первого сквозного демо

### 1. Разложение улучшения кандидата

В `find_improvements` поле `delta` вычисляется относительно пользовательского набора, а `decomposition` копируется из evaluate и относится к базе. Эксперимент на первом кандидате контрольного набора: delta=0.66249, сумма decomposition=4.64788.

Минимальная правка:

```python
"decomposition": {
    key: r["decomposition"][key] - orig["decomposition"][key]
    for key in ("avg", "min", "crit")
},
```

Добавить тест равенства суммы трёх слагаемых `candidate["delta"]` с допуском 1e-6. Это ошибка вычисляемого ответа, её не откладывать как улучшение инфраструктуры.

### 2. Проверка объяснения

`_validate_answer` принял как корректный ответ `{"summary":"Score 999, budget 10000"}` и утверждение `Score 999` со ссылкой `f1`. Проверка существования ID не проверяет соответствие текста факту. Приведение произвольного значения через str и обрезка длины также не заменяют строгую схему.

Минимум: строгие типы, обязательные summary/strengths/risks/suggestions, непустые ссылки у утверждений и проверка candidate_id. Числовые токены `{{f7.after}}` внедрять необязательно. Более простой режим: модель даёт качественный текст со ссылками, а числовые значения отображаются отдельными серверными фактами; ответы с цифровыми числами в свободном тексте отклоняются. Формат и ограничения согласовать с фронтендом. Такая проверка не доказывает истинность качественных утверждений или чисел прописью; не заявлять полную защиту от выдумок.

Тесты: неполная схема, неверный тип, неизвестная ссылка, выдуманное число → fallback; корректный ответ → live. Тест без ключа должен требовать ровно fallback и отсутствие обращения к провайдеру, а не принимать оба режима.

### 3. Риски резервного объяснения

На примере из ТЗ fallback возвращает risks=[]. Поиск подстрок «Критические показатели» и «без изменений» не выявляет сохраняющиеся слабые показатели, отрицательные эффекты и ограничения сценария.

Формировать риски из расчёта: оставшиеся критические пары; отрицательные изменения; низкие неизменившиеся показатели. Если таких пунктов нет, дать честное пояснение границ модели. Добавить проверку контрольного сценария; риски не выдумывать для заполнения списка.

### 4. Воспроизводимость

Убрать удаление фиксированной папки TEMP и клонирование проекта за пределы текущего репозитория. Чистую проверку выполнить в новой среде внутри репозитория на предназначенных к сдаче файлах, без личного `.env`. Не проверять старую удалённую версию вместо текущих изменений.

Сложный `run.py` с автосозданием среды не обязателен. Требование понятного воспроизводимого запуска остаётся: документировать и проверить точную последовательность установки и одну команду запуска. Если нужна единая команда с установкой, достаточно небольшого проверенного launcher без кэша установок и сложного управления процессами.

## Можно отложить

- Bootstrap с хешем requirements и отдельными тестами subprocess.
- Разделение на settings.py, api_models.py, requirements-dev.txt: это организационные решения, допустимо оставить компактно в существующих файлах.
- Асинхронный Protocol провайдера. Обычные sync-маршруты плана совместимы с синхронным клиентом; не переносить блокирующий вызов в async-маршрут.
- Тест вытеснения кэша на 101 сценарии; сохранить существующее ограничение размера и тест повторного запроса.
- Язык шаблонных числовых вставок при выбранной более простой границе между текстом модели и серверными числами.
- Полный потоковый лимит ASGI, если команда сознательно снижает его приоритет. До исправления нельзя утверждать, что лимит тела 16 КБ гарантирован: в плане проверяется только Content-Length. Записать ограничение в общей спецификации, если откладывается.

## Приоритет исполнения

Сначала валидатор и точный расчёт; затем HTTP и вклад мер; затем советник с исправленным разложением, содержательный fallback и проверенный live; затем сквозное демо, README и чистый запуск. Улучшения инфраструктуры брать только после этого. Commit и push требуют разрешения пользователя.
