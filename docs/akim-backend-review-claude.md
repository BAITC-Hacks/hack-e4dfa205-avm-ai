## Недочёты

### Н1. Падение ядра на `measure_id: null`

`engine/scoring.py`, функция `normalize`: `d.get("measure_id", "")` возвращает `None`, если ключ есть со значением `null`, дальше `_measure_number(None)` падает с `TypeError`. `validate` в `engine/validator.py` тот же вход обрабатывает корректно и даёт `unknown_measure`, но `evaluate` вызывает `scenario_key` до проверки ошибок. Через HTTP не воспроизводится: pydantic в строгом режиме отклоняет `null` для строкового поля с 422. Для ядра, которое вызывается из советника и тестов напрямую, это дефект.

Правка в `engine/scoring.py`:

```python
def normalize(decisions: list) -> list:
    out = []
    for d in decisions:
        if not isinstance(d, dict):
            d = {}
        mid = str(d.get("measure_id") or "")
        did = d.get("district_id") or None
        out.append({"measure_id": mid, "district_id": str(did)} if did else {"measure_id": mid})
    return sorted(out, key=lambda x: (_measure_number(x["measure_id"]), x.get("district_id") or ""))
```

Тест в `tests/test_scoring.py`:

```python
def test_null_measure_id_is_error_not_crash():
    r = evaluate(CITY, [{"measure_id": None}] + EXAMPLE[1:])
    assert r["valid"] is False and any(e["code"] == "unknown_measure" for e in r["errors"])
```

### Н2. Ядро принимает не-словари

`engine/validator.py`, функция `validate`: элемент набора, который не является `dict`, даёт `AttributeError` на `d.get`. Через HTTP не воспроизводится. Правка в начале цикла:

```python
    for i, d in enumerate(decisions):
        if not isinstance(d, dict):
            errors.append(_err("unknown_measure", "Решение должно быть объектом с measure_id", [], [i]))
            continue
```

### Н3. Повторы среди невалидных строк не считаются

`engine/validator.py`: `duplicate_measure` ищется только среди строк, прошедших проверку ID и района. Набор из пяти `{"measure_id": "M1"}` без района даёт пять `district_required` и ни одной `duplicate_measure`. Пользователь ошибку увидит, но подсветка повтора теряется. Правка: считать позиции по `measure_id` до фильтрации.

```python
    positions = defaultdict(list)
    for i, d in enumerate(decisions):
        if isinstance(d, dict) and d.get("measure_id") in city.measures:
            positions[d["measure_id"]].append(i)
```

и убрать прежнее заполнение `positions` из `known`.

### Н4. Резерв может назвать «сильной стороной» отрицательное слагаемое

`engine/facts.py`, функция `fallback_explanation`: факт `decomposition` всегда попадает в сильные стороны, даже если все три слагаемых отрицательны. Такой набор возможен из-за `M11` с эффектом `T1 −2` при слабых остальных мерах. Правка:

```python
    dec = of("decomposition")[0]
    strengths = [item(dec)] if any(v > 0 for v in dec["data"].values()) else []
```

и в риски добавить факт разложения, если `sum(dec["data"].values()) < 0`.

### Н5. База пересчитывается при каждом вызове

`engine/scoring.py`, функция `evaluate`: `apply_effects(city, [])` и `aggregate` вызываются на каждом расчёте, советник делает это 270 раз на запрос. При 16 мс на весь перебор это не проблема, но кэш базы по `city.version` через `functools.lru_cache` убирает лишнюю работу. Необязательно.

## Что в порядке и не требует правок

- Правила валидатора соответствуют ТЗ: ровно 5, бюджет ≤ 100, повторы, не более 2 из направления, M1/M3 везде, M4/M7 и M5/M13 в одном районе, район обязателен и запрещён где нужно.
- Обрезка 0–100 один раз после суммирования, лаг применяется к эффектам, синергии без лага, порог строго меньше 40, порядок решений не влияет на результат и ключ.
- Датасет проверяется при загрузке, исходные данные не мутируют.
- Советник честно ограничен заменой одной меры, дельта и разложение считаются от набора пользователя.
- Факты и резерв не выдумывают числа, риски формируются правилами.
- `.gitignore` дополнен кэшем Python и pytest, это правильно, в плане этого не было.
