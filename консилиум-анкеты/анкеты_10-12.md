### 3. Критерии оценки
- Таблицы с баллами в ТЗ трека 10 нет.
- Есть Must have с формулировкой «проверка» на каждый пункт (по сути acceptance-тесты):
  1. Запрос по существующему артикулу → верные наличие, характеристики, ссылка/файл сертификата (если есть в базе).
  2. Запрос по позиции с нулевым остатком → минимум один аналог с кратким обоснованием.
  3. Вопрос об условиях покупки → содержательный ответ.
  4. Без явного «да, добавь» корзина не меняется; после подтверждения количество не превышает остаток.
  5. После добавления — прямая ссылка на корзину, ведущая на актуальное состояние.
- Объективной метрики нет; оценка качественная, по прогону сценариев.

### 5. Обязательные технологии/ограничения

### 6. Внешние зависимости при проверке
- API ekt.kz (basicAuth) — реальная внешняя зависимость. ТЗ прямо разрешает синтетический/анонимизированный каталог, значит кэш/снапшот каталога в репозитории — легитимная заглушка.
- Корзина: API для добавления в корзину ekt.kz в материалах не дан (только чтение каталога). Корзину придётся эмулировать на своей стороне (своя страница корзины со ссылкой) — ТЗ это не запрещает, пункт 5 требует лишь ссылку на актуальное состояние корзины.
- LLM: не указана; нужна любая LLM с function calling. Заменить заглушкой без потери смысла нельзя, но можно кэшировать демо-ответы на случай сбоя.
- Распознавание вложений (PDF/Excel/фото) — при отсутствии тестовых файлов можно показать на своём примере.

### 7. Минимальный рабочий срез за 3,5 часа
1. Скрипт выгрузки каталога через API в JSON/SQLite (первые N страниц + детали), проверить реальные поля.
2. Бэкенд (FastAPI/Node): tools для LLM: `search_products`, `get_product`, `find_analogs` (по категории + характеристикам), `get_purchase_terms` (статический текст), `add_to_cart` (только при явном подтверждении, clamp по остатку), `get_cart_link`.
3. Простая веб-страница с чатом (адаптивная), своя серверная корзина + страница `/cart/<session>`.
4. Системный промпт: не менять корзину без явного «да», не выдумывать цену/наличие, объяснять выбор аналога.
5. README с архитектурой, запуском, описанием данных. Пять сценариев из Must have прогнать вручную и записать в README примеры артикулов.
- Вложения (PDF/Excel/фото): минимально — извлечение артикулов из текста PDF/Excel; фото — при наличии мультимодальной LLM.

### 8. Пожиратели времени и риски
- Реальный API: неизвестный формат, объём, скорость, возможные отсутствующие поля (остатки, сертификаты, характеристики). Если данных для «аналогов» и «сертификатов» в API нет — придётся досинтезировать.
- Аналоги: без структурированных характеристик поиск аналога превращается в угадывание. Нужен понятный алгоритм (та же категория + близкие параметры + в наличии) с текстовым обоснованием.
- Корзина: интеграции с настоящей корзиной сайта нет, придётся честно объяснить эмуляцию.
- Парсинг вложений (накладная, спецификация, фото) — легко утонуть; делать в последнюю очередь.
- Галлюцинации по цене/наличию — прямое нарушение ограничений ТЗ; все числа только из tool-результатов.

### 9. Где выделиться
- Большинство сделает RAG-чат по каталогу. Неочевидное: строгий guardrail «корзина только через подтверждение» показан как отдельная проверяемая логика (лог событий корзины, аудит действий), объяснимость аналога в виде таблицы сравнения характеристик «запрошено vs предложено».
- Загрузка спецификации/накладной (Excel/PDF) → массовая проверка наличия по списку позиций → одно подтверждение → корзина. Это закупщик от компании — ключевой пользователь по ТЗ.
- Казахский язык (опционально в ТЗ) — дешёво добавить через LLM.
- Эскалация на менеджера при неуверенности (опционально в ТЗ).

### 10. Ценностная история
- Владелец: ТОО «Электрокомплект», ekt.kz.
- Проблема: клиенты пишут/звонят менеджеру по характеристикам, наличию, аналогам, условиям — решение о покупке затягивается, часть уходит к конкурентам, менеджеры тратят время на однотипные вопросы.

### 2. Входные данные
- Полностью заданы в доп. документе (текст в Задачи.md, строки 4058-4380), внешних файлов нет:
  - 5 районов (Есиль 0.27, Алматы 0.24, Сарыарка 0.20, Байконур 0.13, Нура 0.16 доли населения) × 10 показателей (T1, T2, E1, E2, S1, S2, B1, B2, C1, C2), шкала 0-100, все «чем больше, тем лучше». Исходные значения и итог D по районам даны.
  - 14 мероприятий M1-M14: направление, тип (Район/Город), стоимость, лаг L, эффекты по показателям.
  - 3 синергии (M1+M2, M10+M12, M5+M6), 3 несовместимости (M1/M3 везде; M4/M7 в одном районе; M5/M13 в одном районе).
  - Веса показателей w_k (сумма 1), формула Score.
  - Правила: бюджет 100, ровно 5 решений, без повторов, район обязателен для типа «Район», не более 2 мер из одного направления, невалидный набор → Score не считается, валидатор возвращает причину.
  - Контрольные числа: базовый Score 52.56; пример набора (M7 Нура, M8 Нура, M10 Нура, M12 город, M5 Сарыарка) стоимость 95, Score ≈ 56.5; самый дешёвый валидный набор M9+M11+M10+M12+M4 = 61.
- Данные чистые, синтетические, добывать извне ничего не нужно.

### 4. Как проверяют
- По формулировке критериев — ручной прогон: ввести набор, проверить блокировку превышения бюджета, изменить набор и увидеть изменение Score, прочитать объяснение. Скрытый тест, AI-судья: в ТЗ не указано.

### 5. Обязательные технологии/ограничения
- Стек, LLM: не указаны.
- Жёстко: «Роль ИИ: LLM получает результат расчёта (дельты по районам и показателям, вклад каждой меры) и объясняет его, сравнивает наборы, советует. Числа он не считает и не придумывает.» Расчёт — детерминированный код.
- Формула Score фиксирована: I' = clip(I + Σ эффект × (8−L)/8 + синергии, 0, 100); D_d = Σ w_k I'; D_avg = Σ pop_d D_d; Score = 0.7·D_avg + 0.3·min(D_d) − 1.0·N_crit (N_crit — пары район×показатель < 40).
- Синергия: бонус фиксированный, лагом не масштабируется, для «Район» — в районе первой меры пары.
- Ровно 5 решений, не «до 5». Остаток бюджета не сгорает и не даёт бонуса. Порядок решений не важен.
- Латентность, языки: не указаны.

### 6. Внешние зависимости при проверке
- LLM для объяснения — единственная внешняя зависимость. Легко заменяется: шаблонное объяснение из посчитанных дельт как fallback (топ-вклады мер, слабейший район, критические значения). Сам расчёт полностью локальный.

### 7. Минимальный рабочий срез за 3,5 часа
1. Модуль данных: районы, показатели, веса, 14 мер, синергии, несовместимости — в одном JSON/py-файле.
2. Валидатор (все 8 правил) с текстовой причиной отказа; движок расчёта Score с разложением вклада по мерам и районам.
3. Тесты: базовый 52.56; пример 95 / ≈56.5; дешёвый набор 61 валиден; M1+M3 отвергается и т.д.
4. UI: выбор 5 мер с районом, живой счётчик бюджета, блокировка сверх 100, кнопка «Рассчитать» → Score, таблица до/после по районам, N_crit.
5. LLM-объяснение по структурированному JSON расчёта: сильные стороны, риски, компромиссы; fallback без LLM.

### 8. Пожиратели времени и риски
- Ошибка в мелочах формулы: лаг (8−L)/8, синергии без лага и «в районе первой меры», clip до подсчёта N_crit, «строго меньше 40», штраф −1 за пару. Контрольные числа обязательны как тесты.
- Соблазн отдать расчёт LLM — прямое нарушение ТЗ.
- Перебор UI (карты, анимации) вместо корректности.
- «Единый бюджет для всех пользователей» и «сравнение команд» — потребуют хранилища сессий, если делать.

### 9. Где выделиться
- Большинство: форма + расчёт + текст от LLM. Неочевидно:
  - Полный перебор всех валидных наборов (14 мер × районы — конечное и небольшое пространство) → оптимум, Pareto-фронт «стоимость/Score», ранг пользовательского набора среди всех допустимых. LLM объясняет расстояние до оптимума.
  - «Что если»: AI-рекомендации по улучшению (опционально в ТЗ) на базе перебора соседей (замена одной меры).
  - Неожиданные события (опционально): шок в районе → пересчёт → перераспределение.
  - Визуализация до/после по районам (опционально в ТЗ) — дёшево на любой chart-библиотеке.
  - Таблица лидеров команд (опционально) — простой файл/SQLite.
