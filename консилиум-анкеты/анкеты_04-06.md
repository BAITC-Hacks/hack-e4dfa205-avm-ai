### 4. Как проверяют
- Одна команда: `python local_eval.py` тем же кодом, что на судействе, но эффекты на судействе другие (скрытые).
- Must-have проверки: агент запускается без ошибок; 1–10 корректных кампаний (нет строк «Кампания … отброшена»); «Пилотов проведено > 0» и логика видна в коде; лимиты не превышены; `submission.csv` воспроизводится.
- Код автоматически проверяется на «залезание» во внутренности env (`__closure__`, `gc`, чтение файлов организатора) — аннулирование.
- `--runs 10` — устойчивость по seed (опционально, «знак не должен скакать»).

### 5. Обязательные технологии / ограничения
- Python (`agent.py`, интерфейс `act(env)`).
- Лимиты одновременно: ≤10 кампаний; ≤5 000 абонентов на кампанию; ≤15 000 контактов всего, включая пилоты; бюджет 100 000 у.е. включая пилоты; ≤20 пилотов по 10–200 абонентов; абонент считается один раз по лучшей для него кампании.
- Каналы: push (0 у.е., ×0.50), sms (4, ×0.65), digital_ads (22, ×0.85), call (160, ×1.20).
- Агент работает ≤10 минут, включая все вызовы LLM.
- Ключ LLM только из `os.environ["OPENAI_API_KEY"]` — на судействе подставят организаторы. Хардкод секретов запрещён.
- «Настраивайте логику, а не константы под мок».

### 6. Внешние зависимости при проверке
- LLM опционален («разрешено и приветствуется»). Если используется — через OpenAI-ключ из env, организаторы подставят свой.
- Обязательно: try/except вокруг вызовов LLM и запасная логика. Если агент упадёт, пилоты всё равно засчитаются, а результат будет отрицательным.
- Полностью офлайн-решение без LLM допустимо по ТЗ.

### 7. Минимальный рабочий срез (3,5 часа)
1. Из `change_tariff.csv` посчитать средний относительный прирост ARPU для пар (текущий тариф/сегмент → целевой тариф) — априорная оценка.
2. Выбрать 10–15 кандидатов (сегмент × целевой тариф) с лучшим ожидаемым uplift × численность сегмента.
3. Пилоты: сначала малые (30–50) на кандидатах, добавить абонентов победителям (адаптивно), считать доверительный интервал по размеру пилота.
4. Финальный отбор ≤10 кампаний по нижней границе интервала, канал по ценности сегмента (push для LOW, sms/ads для MID, call только на HIGH с высоким uplift), проверка лимитов (контакты, бюджет, 5 000 на кампанию, уникальность абонентов).
5. Прогнать `local_eval.py`, `--runs 10`, `make_submission.py`, README.
LLM можно добавить как слой формулировки гипотез/объяснений плана, с fallback.

### 8. Пожиратели времени и риски
- Незнакомый API env: как именно `run_pilot` возвращает результат и что в `pilot_history` — узнаётся только из пакета.
- Отрицательный результат из-за перерасхода на call/ads или дублирования абонентов между кампаниями.
- Оверфит под мок-эффекты — на судействе эффекты другие.
- Шум пилотов (30 клиентов ошибаются в 1 из 4 случаев) — без учёта неопределённости результат скачет по seed.
- Лимит 10 минут при использовании LLM.
- Соблазн «подсмотреть» в env — аннулирование.

### 9. Где выделиться
- Очевидное: пилоты фиксированного размера на всех кандидатах, один канал на всё.
- Неочевидное: последовательный дизайн пилотов (bandit/Thompson sampling или successive halving), явные интервалы неопределённости, распределение бюджета через ожидаемую ценность информации, выбор канала как оптимизация «uplift × множитель − стоимость» по сегменту ARPU, устойчивость по `--runs 10` с графиком в README.
- LLM в роли «аналитика»: объясняет план на человеческом языке для маркетолога (совпадает с пользователем из ТЗ).

### 10. Ценностная история
- Владелец: Билайн. Пользователь: аналитик маркетинга, планирующий кампании на следующий месяц.
- Проблема: кампании «вслепую» дают downsell, ручной перебор вариантов не успевает; стратегия без разведки приносит ~15 раз меньше.
- Масштабируемость: тот же контур «пилот → оценка → план» применим к любой базе абонентов и другим офферам (по ТЗ прямо не заявлено, следует из постановки).

### 1. Что сдать

- README — да: методология расчёта, описание алгоритма исключения выбросов, инструкция запуска.

### 2. Входные данные
- Материалы: `IEK.zip` (9.9 МБ), `Systeme electric.zip` (2.9 МБ) — содержимое в ТЗ не описано (по названиям — данные по двум поставщикам/брендам).
- По ТЗ вход: история продаж (дата, артикул, количество, обезличенный клиент, цена), текущие остатки по складам, периоды stockout по артикулам, справочник поставщиков и сроков поставки, материальная ведомость из 1С.
- «Партнёр предоставит отчёт V2 и данные по динамике продаж (образец предоставляется партнёром, полный набор и точная дата выдачи — по согласованию)». Объём: «история за продолжительный период (порядок объёма уточняется партнёром)».
- Допустимы синтетические данные с реалистичным распределением для разработки и тестирования.
- Чистота данных — в ТЗ не указана; наличие в архивах всех перечисленных источников (в пути, stockout, справочник поставщиков) — в ТЗ не подтверждено, проверять по факту.

### 3. Критерии оценки
- Таблица критериев с баллами в ТЗ трека отсутствует (в отличие от 04 и 06).
- Объективной метрики (MAE и т.п.) нет. Оценка качественная по 5 must-have с описанными проверками:
  1. Базовая потребность по каждому артикулу с учётом всех источников; изменение любого источника (например, товаров в пути) отражается на результате.
  2. Сезонность и устойчивый рост: для сезонного товара прогноз отражает паттерн, а не среднее.
  3. Упущенный спрос при stockout: потребность скорректирована вверх относительно «сырых» продаж.
  4. Разовые крупные заказы (включая крупные продажи одному клиенту): искусственно добавленный выброс не поднимает регулярное количество существенно.
  5. Итоговый список по поставщикам с обоснованием каждой строки.

### 4. Как проверяют
- По тексту must-have: «на тестовом наборе данных» формируется список; проверяющие могут менять входы (объём в пути), искусственно добавлять крупный заказ, смотреть сезонный товар и артикул со stockout. Это описание ручного/сценарного прогона.
- Скрытый тест, AI-судья — в ТЗ не указаны.

### 5. Обязательные технологии / ограничения
- Стек — в ТЗ не указан.
- Нельзя: автоматически отправлять заказ поставщику без подтверждения сотрудника; использовать неанонимизированные данные о клиентах.
- Обязательно: приватность данных, объяснимость расчёта, устойчивость к аномалиям и выбросам, совместимость выходного формата с текущей учётной системой компании (1С упоминается как источник материальной ведомости; конкретный формат — в ТЗ не указан).

### 6. Внешние зависимости при проверке
- В ТЗ не указаны. Задача решается локально на файлах; LLM не требуется. Если LLM используется для текста обоснований — заменяем шаблонными обоснованиями из чисел (детерминированно и безопаснее).

### 7. Минимальный рабочий срез (3,5 часа)
1. Разобрать архивы, привести продажи к таблице «дата × артикул × количество × клиент × цена», остатки — к «артикул × склад × остаток».
2. Очистка выбросов: по артикулу — строка с количеством > k·медианы (или квантиль 95–99 по клиенту/дню) помечается как разовый заказ и исключается из регулярного спроса; отдельно — доля одного клиента.
3. Прогноз: недельный/месячный спрос = скользящее среднее × сезонный коэффициент (месяц/квартал к среднему) × тренд (линейный наклон последних N месяцев).
4. Stockout: дни без остатка исключаются из знаменателя (спрос считается по дням в наличии) — потребность растёт.
5. Заказ = спрос на (срок поставки + период обзора) + страховой запас − остаток − в пути; срочность по дням до обнуления остатка.
6. Вывод: CSV/XLSX + простой дашборд (Streamlit или таблица в HTML), группировка по поставщику, текстовое обоснование из компонентов формулы, кнопка «утвердить» без отправки.
7. README с методологией и алгоритмом выбросов.

### 8. Пожиратели времени и риски
- Неизвестная структура архивов (1С-выгрузки, Excel с объединёнными ячейками, кодировки) — самый большой риск, парсинг может съесть час.
- Отсутствие в данных «товаров в пути», stockout и справочника поставщиков — придётся синтезировать и честно пометить.
- Соблазн тяжёлого ML (Prophet и т.п.) вместо прозрачной формулы; жюри проверяет объяснимость и реакцию на изменение входов.
- Проверка «добавили выброс — количество не выросло» ломается, если порог выбросов задан слабо.

### 9. Где выделиться
- Очевидное: среднее по истории + фиксированный порог выброса, вывод в таблицу.
- Неочевидное: обоснование в виде разложения числа («спрос 120/мес × сезон 1.3 × рост 1.05 − остаток 90 − в пути 40 + страховой 25»); режим «что если» с ползунками (в пути, срок поставки) прямо показывает must-have 1; детектор выбросов с объяснением, какая продажа исключена и почему; приоритизация по дням до дефицита (опционально в ТЗ); экспорт в формат, похожий на 1С-заказ.

### 10. Ценностная история
- Владелец: ТОО «Электрокомплект» (ekt.kz), дистрибьютор электротехники. Пользователь: менеджер отдела закупа.
- Проблема: ручной Excel, расчёт редкий, избыток по одним позициям и дефицит по другим, разовые крупные продажи искажают регулярную потребность.
- Ценность по ТЗ: снижение издержек хранения, меньше дефицита и упущенных продаж, точнее закупочные решения.
- Масштабируемость: те же данные есть у любого дистрибьютора с 1С; формула переносится на любой склад/категорию (по ТЗ прямо не заявлено).

### 11. Особые заметки
- Единственный из трёх треков без таблицы баллов в ТЗ.
- Призы, OpenAI, NVIDIA, казахский язык — в ТЗ не упоминаются.

- Стек, лимит латентности жёсткий — в ТЗ ориентир 10 секунд.

### 6. Внешние зависимости при проверке
- LLM/эмбеддинги опциональны. Если LLM генерирует объяснения — риск недетерминизма и латентности; нужен fallback на шаблонные объяснения из фактов (бюджет, формат, язык, часы, совпадение по описанию).
- Полностью офлайн-вариант (правила + TF-IDF/локальные эмбеддинги) закрывает все требования ТЗ.

### 7. Минимальный рабочий срез (3,5 часа)
1. Загрузить jsonl, нормализовать категории/форматы/города.
2. Фильтр-каскад с фиксацией причин отсева: город → категория (если пусто: исход «нет категории в городе») → дата не в `busy_dates` → формат → бюджет (`price_from_kzt` ≤ бюджет) → язык → `max_hours` ≥ длительность (если не null). Если после фильтров пусто — исход «кандидаты есть, но не проходят» с перечислением причин по каждому.
3. Ранжирование детерминированное: запас по бюджету, совпадение языка, семантическая близость описания к типу мероприятия (TF-IDF или эмбеддинги с кэшем), тай-брейк по `id`.
4. Объяснение: шаблон из конкретных фактов карточки («укладывается в бюджет 300 000 ₸ при цене от 250 000; ведёт на казахском; в описании — опыт с той на 200 гостей»). Опционально LLM-перефраз с `temperature=0`, seed и fallback.
5. Тонкий интерфейс: CLI/FastAPI/Streamlit с пометкой synthetic-профилей.
6. Три демо-запроса заготовлены, README с описанием пайплайна.

### 8. Пожиратели времени и риски
- Недетерминизм LLM ломает пункт «тот же порядок» и «объяснения не взаимозаменяемы» — ранжирование делать без LLM.
- Общие фразы в объяснениях — прямое нарушение ТЗ.
- Неаккуратная обработка `max_hours = null`, «Зарубежье», множественных категорий.
- Пустой результат как ошибка/пустой экран.
- Трата времени на UI вместо объяснений.

### 9. Где выделиться
- Очевидное: фильтр + LLM-текст «почему подходит».
- Неочевидное: явный «след отсева» (сколько кандидатов было и по какой причине выбыл каждый — это прямо закрывает исход 3 и пункт «почему меньше трёх»); объяснение-контраст между карточками («дешевле №1 на 80 000 ₸, но без английского»); ближайшие свободные даты у занятых подрядчиков как подсказка (без бронирования); декабрьский сценарий «выходные заняты — это сезон»; пометка синтетических профилей в выдаче.

### 10. Ценностная история
- Владелец: Firebird, площадка-агрегатор event-подрядчиков в Казахстане.
- Проблема: заказчик получил каталог по городу и не может выбрать; сервис сокращает выбор до 3 с объяснением. «Ценность в объяснении, а не в сортировке».
- Масштабируемость: та же схема на любую категорию, включая площадки; данных можно добавлять в том же формате (по ТЗ прямо про масштаб не сказано).
