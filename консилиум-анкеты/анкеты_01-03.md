## 01. Энергетика — Agentic AI для прогноза выработки ВЭС (Самрук-Казына)

**1. Deliverables.** В ТЗ явно: решение, которое (а) строит модель почасового прогноза по истории, (б) само тянет погодные прогнозы по координатам из открытых источников, (в) выдаёт прогноз на 24–48 ч с почасовой детализацией, (г) работает как Agentic AI с полным циклом «погода → подготовка → модель → прогноз → анализ → пересчёт при обновлении входа». Нужно воспроизвести последовательные прогнозы: 31 января → на 24–48 ч, 1 февраля → новый, и так по всему февралю 2026. Формат файла прогноза, API, UI, презентация — в ТЗ не указаны. README и репозиторий подразумеваются критерием «README и воспроизводимость» (25 баллов).

**2. Входные данные.** Два CSV (turbine 1 — 5.8 МБ, turbine 2 — 6.1 МБ), 11.03.2023–28.02.2026 по названию файлов (в тексте ТЗ история «до 31 января 2026 включительно», тест — февраль 2026; т.е. файлы, судя по названию, содержат и февраль — факт февраля, вероятно, внутри, но ТЗ этого не оговаривает). Колонки: статистическое время, средняя скорость ветра м/с, нормализованная активная мощность на стороне линии, средняя температура °C. Координаты турбин — две ссылки Google Maps (координаты нужно извлечь из ссылок). Чистота данных, шаг времени (10 мин / час), пропуски — в ТЗ не указаны. Извне добывать обязательно: архивные прогнозы погоды (не факт!) по координатам на каждую дату февраля.

**3. Критерии.** Стандартная таблица 25/25/25/15/10. Объективной метрики (MAE/RMSE) в ТЗ нет. Оценка качественная/экспертная.

**4. Как проверяют.** В ТЗ не описано (нет тестового набора, нет AI-судьи). По критерию README — «возможность воспроизвести и проверить решение на основании материалов репозитория», т.е. ожидаем ручной прогон по README.

**5. Обязательные технологии/ограничения.** Стек свободный («выбор источников погоды, ML-моделей, методов, архитектуры агента — за участниками»). Жёсткое требование: для каждого прогноза использовать архивные прогнозы погоды, доступные на тот момент, а не факт. Горизонт 24–48 ч, почасовая детализация. Языки, латентность — не указаны.

**6. Внешние зависимости.** Источник архивных прогнозов погоды (открытый) — обязателен по сути задачи; ТЗ его не называет. LLM для агентного слоя — не обязателен по ТЗ. Заглушка допустима технически (кэшировать скачанные прогнозы февраля в репо, чтобы проверка шла офлайн), при этом сам код получения из внешнего источника должен быть — иначе не выполнен п. 2 задачи.

**7. Минимальный срез за 3,5 ч.**
- Скачать CSV, привести к часу, склеить с историческими прогнозами погоды (нужен источник с archive-forecast по lat/lon; конкретный сервис ТЗ не задаёт).
- Модель: регрессия мощности от прогнозной скорости ветра/температуры (градиентный бустинг или даже кривая мощности по истории).
- Цикл по дням 31.01→28.02: на каждый день взять прогноз, доступный на этот момент, выдать 48 часов, сохранить в файл; сравнить с фактом, если он есть в CSV (самооценка MAE).
- Агентная обёртка: оркестратор, который прогоняет шаги «получить погоду → подготовить → предсказать → проанализировать → пересчитать», логирует и умеет перезапуститься при обновлении входа.
- README с одной командой запуска.

**8. Пожиратели времени / риски.**
- Главный: найти открытый источник именно архивных прогнозов (с датой выпуска), а не реанализа. Если источника нет — требование п. 2 формально не выполнимо честно.
- Извлечь координаты из коротких ссылок Google Maps.
- Резолюция и пропуски в CSV (неизвестны).
- Соблазн утечки: использовать фактическую погоду вместо прогноза — прямо запрещено ТЗ.
- ML-валидация в 3,5 ч — только грубая.

**9. Где выделиться.** Большинство сделает бустинг + скрипт-цикл и назовёт это агентом. Неочевидное: честный «as-of» протокол (лог, какой прогноз какого выпуска использован для какого часа), агент-шаг «анализ результата» с автоматическим объяснением промахов (например, обледенение при отрицательной температуре, curtailment), пересчёт при обновлении прогноза в течение дня (несколько выпусков в сутки), отдельные модели для двух турбин с проверкой согласованности.

**10. История для жюри.** Владелец — Самрук-Казына (энергохолдинг). Проблема: ВЭС должна подавать почасовой график на сутки–двое вперёд; ошибка прогноза — дисбаланс и штрафы. Масштаб: та же схема на любую ВЭС/СЭС по координатам — агент только меняет точку и историю.

**11. Особые заметки.** ТЗ дано на RU/KZ/EN, требований к языку интерфейса нет. Призов/обязательного OpenAI/NVIDIA — не указано. Необычное: требование воспроизвести прогноз «как в прошлом» с архивными прогнозами — единственная содержательная ловушка задачи.

## 02. Финансы — «Граф денег» (Freedom)

**1. Deliverables.** Обязательные артефакты (таблица п. 10): репозиторий (пайплайн + интерфейс); README (одна команда запуска, критерии ролей и пороги, что на выходе, ограничения, раздел про масштабирование до ~1 млн узлов текстом); три CSV фиксированной схемы: `nodes_roles.csv` (2 248 строк: gid, role, role_score 0–1, cluster_id, priority_score 0–1, evidence ≤200 символов), `clusters.csv` (cluster_id, n_nodes, n_seed, sum_kzt_internal, top_gids, hypothesis), `top_nodes.csv` (≥20 строк: rank, gid, role, priority_score, why); схема решения — один слайд «данные → метрики → роли → интерфейс»; демо 5 минут: живой прогон + разбор 2–3 узлов. Экран просмотра: схема сети с направлением потоков, подсветкой ролей/кластеров, поиском по gid (веб, ноутбук или desktop — на выбор).

**2. Входные данные.** Архив data/ (85 КБ): `edges.parquet` (3 119: src, dst, sum_kzt, n_tx, depth), `nodes.parquet` (2 248: gid, depth, is_seed), `transactions.parquet` (4 840: src, dst, date, sum_kzt). Период июль 2026, только исходящие переводы от 81 seed на 4 колена, порог 5 000 KZT, внутрибанк. Плюс README датасета и starter/ (загрузка, сборка графа, базовые метрики, шаблоны выгрузок). Данные обезличены, атрибутов клиентов нет. Известные дефекты объявлены заранее и их учёт оценивается: 444 узла depth=4 с нулевым исходом — артефакт обрыва; входящие извне не видны; у seed занижен вход (354 узла отдают больше, чем получили); 19 seed нет в рёбрах, 12 только получатели, 31 без исходящих; 16 компонент (1 877 / 270 / 14 мелких). Внешние источники не требуются и запрещены.

**3. Критерии.** Стандартная таблица 25/25/25/15/10. Ground truth нет: «оценка — по обоснованности критериев, а не по accuracy». Объективной метрики нет. Дополнительно — 5 must-have, без которых решение «не считается выполненным».

**4. Как проверяют.** Явно расписано: (1) жюри запускает команду из README на чистой машине, пайплайн <5 мин, создаёт 3 файла; (2) nodes_roles.csv — 2 248 строк, все колонки, evidence непустой; (3) жюри называет 3 произвольных gid — команда за минуту объясняет роль через свои метрики; (4) clusters.csv заполнен, cluster_id у каждого узла; (5) на демо жюри называет gid — команда находит его на схеме и показывает связи. Ручной прогон + устный допрос.

**5. Обязательные технологии/ограничения.** Стек любой, рекомендован Python (pandas, networkx/igraph). Полный пересчёт ≤5 мин локально на обычном ноутбуке. Всё локально; интернет — только для внешнего LLM API, если используется. Нельзя: хардкодить gid, «чёрный ящик» без объяснимого правила, обогащать внешними данными/атрибутами, требовать облако/GPU/платные сервисы. Обязательно: explainability для каждой роли и позиции топ-листа, приватность, осторожные формулировки («признаки консолидации», не вина), раздел про масштабирование в README.

**6. Внешние зависимости.** Нет обязательных. LLM опционален (AI-ассистент аналитика, генерация карточек/гипотез). Если LLM используется — воспроизводимость на чистой машине без ключа под угрозой, значит evidence/why должны генерироваться правилами, LLM только сверху и с fallback.

**7. Минимальный срез за 3,5 ч.**
- Взять starter, посчитать на графе: in/out degree, число уникальных плательщиков/получателей, sum_in/sum_out, pass-through ratio, depth, betweenness/PageRank, Louvain-кластеры.
- Правила ролей с порогами: consolidator (≥N уникальных плательщиков, удерживает), transit (ratio 0.8–1.2, вход и выход), distributor (веер ≥M получателей), terminal (вход есть, выход 0, depth<4 — с оговоркой об обрыве), coordinator (высокая центральность + связи между кластерами), peripheral (остальное). role_score из расстояния до порога.
- priority_score = взвешенная сумма нормализованных метрик; evidence/why — шаблонные строки из чисел («получает от 11 плательщиков, отдаёт 3%»).
- clusters.csv с hypothesis по шаблону (кол-во seed, оборот, доминирующая роль).
- Экран: pyvis/plotly/Cytoscape.js HTML с направленными рёбрами, цветом по роли, поиском по gid.
- README с одной командой, таблицей порогов, разделом «1 млн узлов».

**8. Пожиратели времени / риски.**
- Визуализация 2 248 узлов интерактивно и с поиском — легко утонуть; лучше показывать компоненту/окрестность gid.
- Пороги ролей: нужно, чтобы каждая роль была непустой и защищаемой на «3 произвольных gid».
- Ловушка depth=4: наивный terminal даст 444 ложных стока — жюри это проверит.
- Ограничение <5 мин и «чистая машина»: зависимости (parquet → pyarrow) должны ставиться одной командой.

**9. Где выделиться.** Очевидное: degree-правила + Louvain + pyvis. Неочевидное из списка опций ТЗ: отделение настоящих terminal от обрезанных на 4-м колене; временные паттерны из transactions (сквозной транзит 1–2 дня, синхронные переводы в один день); циклы/возвраты; устойчивость сети при изъятии топ-N; оценка полноты («какой запрос делать следующим»); NL-ассистент по графу. Плюс честный раздел «что мы не можем знать по этим данным» — ТЗ прямо просит осторожность формулировок.

**10. История для жюри.** Владелец — Freedom (банк). Проблема: аналитик видит 81 «курьера», реальная сеть 2 248; ручная трассировка — часы на узел; блокируют низ, верх восстанавливается за дни. Эффект: ранжированный список с обоснованием за минуты, фокус на точках консолидации. Масштаб: любой AML-кейс, любой банк, рост до 1 млн узлов описан в README.

**11. Особые заметки.** Призов, OpenAI/NVIDIA — не указано. Языковых требований нет. Необычное: самый детально прописанный протокол проверки из трёх треков (must-have + способ проверки для каждого); ТЗ признаёт «нет единственного правильного ответа»; данные крошечные (85 КБ) — вычисления мгновенны, всё время уходит на логику и объяснимость.

## 03. Управление — Career Quest (Halyk Bank)

**1. Deliverables.** Веб-приложение с AI-слоем + репозиторий + README (п. 10: «Репозиторий: да. README: да»). Выход системы: профиль с траекторией; 1–3 рекомендованных шага с обоснованием; обновление прогресса после выполнения; HR-экран. Обязательна загрузка дополнительных профилей и истории в формате датасета (жюри загружает проверочные профили на защите). Презентация, API — в ТЗ не указаны. Геймификация — не обязательна.

**2. Входные данные.** career_quest_dataset.zip (63 КБ): `employees.json` (200 профилей: роль, грейд, стаж, навыки 0–5), `events.json` (40 событий: тип, аудитория, развиваемые навыки, gain, max_level), `activity_history.csv` (24 мес участия, включая пропуски и отказы), `skills.json` (60 навыков hard/soft, требования по грейдам). Синтетические, на английском с переводами на казахский и русский. Правило роста навыка задано в датасете. Можно расширять своими данными при сохранении схемы. Извне ничего добывать не нужно. Чистота — не указана.

**3. Критерии.** Стандартная таблица 25/25/25/15/10. Объективной метрики нет. Но есть три скрытых проверочных профиля, одинаковые для всех команд, сконструированные так, что однофакторное правило на них ошибается (пример: минимальный навык Public Speaking, но три пропуска подобных активностей в истории, а для грейда критичен System Design). Оценка качественная, с квази-тестом.

**4. Как проверяют.** Ручной прогон: открыть произвольного сотрудника; получить 1–3 рекомендации; обоснование минимум по трём факторам (грейд, разрывы по навыкам, история участия, требования следующего уровня); отметить активность выполненной — прогресс и траектория сдвигаются; HR-view показывает проседающие навыки, у кого нет рекомендованного шага, участие по активностям. Жюри загружает 3 проверочных профиля в формате датасета.

**5. Обязательные технологии/ограничения.** Инструменты: любые модели и сервисы, облачные и локальные LLM/STT/TTS. Латентность: интерфейс до 2 с, AI-рекомендация до 10 с. Запуск одной командой. Нельзя: рекомендация по одному полю под видом AI; публичные рейтинги сотрудников по результативности; механики вокруг обязательных процессов (очки за таймшиты); реальные персональные данные. Учесть: приватность (вовлечённость не видна другим сотрудникам), разграничение прав сотрудник/HR, explainability, добровольность.

**6. Внешние зависимости.** LLM не обязателен по ТЗ; обоснование можно строить правилами. Если LLM используется — лимит 10 с и нужен ключ на защите; заглушка/правила как fallback уместны и даже безопаснее для проверочных профилей.

**7. Минимальный срез за 3,5 ч.**
- Загрузчик четырёх файлов + загрузка дополнительных профилей/истории через UI (обязательно — жюри будет загружать).
- Скоринг активностей для сотрудника: gap по навыкам к требованиям следующего грейда (skills.json) × вес критичности × поправка на историю (пропуски/отказы снижают, своевременные прохождения повышают) × аудитория события; исключить уже пройденные и с max_level достигнутым.
- Топ-3 с текстовым обоснованием, где явно перечислены ≥3 фактора с числами.
- Кнопка «выполнено» → применить gain/max_level, пересчитать прогресс и траекторию.
- HR-экран: агрегаты по навыкам с наибольшим средним gap, список без рекомендаций, участие по активностям. Роль сотрудник/HR переключателем.
- README, одна команда.

**8. Пожиратели времени / риски.**
- Проверочные профили: если скоринг однофакторный или история не учтена — провал на защите.
- Формат загрузки должен точно совпадать со схемой датасета (иначе жюри не сможет загрузить).
- UI-обвязка съедает время; ТЗ прямо говорит, что ядро — качество и объяснимость рекомендации.
- LLM-латентность и недетерминизм на защите.

**9. Где выделиться.** Очевидное: gap-скоринг + шаблонное объяснение + две страницы. Неочевидное: явная «траектория» (что нужно до следующего грейда и сколько шагов), учёт истории как поведенческого сигнала (пропуски → предложить другой формат, а не тот же тип), моделирование перехода на грейд (из опций ТЗ), локализация KZ/RU (данные уже с переводами — дёшево), контр-пример прямо в демо: показать проверочный профиль, где «минимальный навык» ошибается, и почему система выбрала иначе.

**10. История для жюри.** Владелец — Halyk Bank. Проблема: бюджет на развитие расходуется полностью, завершаемость низкая, добровольные активности собирают мало — сотрудник не видит, куда ведёт активность. Пользователи: сотрудник 1–5 лет стажа и HR. Масштаб: любая корпорация с грейдами и каталогом обучения; ТЗ подчёркивает, что узкое место — слой принятия решения, который теперь строится на LLM.

**11. Особые заметки.** Зачёт отдельный от Voice Router (трек 09), команды между кейсами не сравниваются. Призов, OpenAI/NVIDIA — не указано. Казахский: опция «качественная локализация интерфейса на казахский и русский», данные уже переведены. Запрет на публичные рейтинги и принуждение — стоит явно сослаться в README/демо.
